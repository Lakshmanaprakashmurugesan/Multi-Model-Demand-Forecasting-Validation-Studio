# Claim Boundaries

This file is intentionally conservative. It distinguishes what can be demonstrated from the source repository from claims that require separate evidence.

## Demonstrated by the unchanged source

- A Streamlit forecasting application exists.
- The source defines Prophet, Prophet + U.S. holidays, XGBoost, LSTM, and Holt-Winters workflows.
- The source defines chronological holdout evaluation.
- The source calculates MAE, RMSE, MAPE, WMAPE, Bias, and a WMAPE-derived score.
- The source includes recursive XGBoost and LSTM multi-period forecasting logic.
- The source includes optional numeric demand drivers, data-preparation controls, diagnostics, and CSV/Excel export.
- The source includes a deterministic synthetic demonstration generator.

## Not demonstrated by this repository alone

- production deployment at a carrier, employer, OEM, or government entity;
- historical employer savings or KPI outcomes;
- adoption by independent organizations;
- national-scale economic impact;
- government endorsement, sponsorship, or partnership;
- patents, licenses, or commercialization;
- rolling-origin cross-validation;
- automatic multi-SKU or multi-location orchestration;
- MEIO integration;
- blockchain functionality;
- calibrated probabilistic forecasting.

## Interpretation of "production-style"
The source-code docstring uses the phrase `production-style Streamlit application`. In this repository, that phrase should be understood as a description of application organization and user-interface/engineering style. It is **not** evidence of production deployment.

## Historical performance claims
Any claim about prior employer results must be supported separately by permissible first-hand letters, records, or other objective corroboration. A present-day public repository can demonstrate current technical capability and progress, but it cannot retroactively prove that a specific historical employer KPI occurred.
